# CLAUDE.md — nonlife-pricing-agent

Full architecture spec is in **CLAUDE_CODE_HANDOFF.md**. This file is the quick operational brief.

## What this project is

Agentic Python tool that supports actuaries in Non-Life insurance pricing model development.
The goal is to distill a GBM into an interpretable GLM, with a human-in-the-loop at every key decision.

**Pipeline:**
```
Actuary sets target + exposure
        ↓
Feature Selection Agent
  → profiles all columns, LLM proposes feature list with actuarial rationale
  → actuary reviews variable by variable (approve / reject / remark)
  → remarks feed back to LLM for a revised proposal (loop until confirmed)
  → approved list saved to project_config.yaml as checkpoint
        ↓
Grouping Agent (for approved categoricals)
  → LLM clusters high-cardinality variables into risk-homogeneous groups
  → actuary reviews and refines
        ↓
GBM trains on approved features
  → LightGBM with MSE on log(premium/exposure) — standard log-rate target
  → Friedman H-statistics rank pairwise interactions among top-N features
  → interactions + model saved as checkpoint in project_config.yaml
        ↓
Distillation Agent
  → LLM proposes main effects (all approved features) + pairwise interaction terms
  → actuary reviews term by term (same loop)
  → approved terms + patsy formula saved to glm_config.yaml
        ↓
GLM fitted on approved terms
  → Gamma GLM with log link, log(exposure) offset via statsmodels
  → coefficients, deviance explained, AIC printed
  → post-fit coefficient review gate: actuary reviews each term's sign/significance,
    rejects suppressor variables or sparse levels; rejected terms are dropped and the
    model is automatically refit until no rejections remain
  → rating factors table: exp(coef) per parameter as multiplicative relativities
```

Every gate above can be worked either via the CLI (`dashboard/approval_gate.py`, terminal A/R/N/S prompts) or the Streamlit dashboard's Layer 2 interactive workbenches — both read/write the same YAML checkpoints.

**Two separate deliverables, not one pipeline with one output:** the GBM (technical/risk price, explores what the data says) and the distilled GLM (commercial tariff, explains effects). A variable can be GBM-relevant but GLM-ineligible (not available at quote time, regulatory, business strategy) — that's why GLM main-effect inclusion needs its own actuary gate even though the variable's GBM inclusion was already decided upstream, not a shared flag.

**Extended 2026-08-30 — finalized snapshots + comment history:**
- Every draft snapshots to disk under `reports/drafts/{initial,modified,finalized}/` — `initial` only from an explicit "Regenerate from scratch" (LLM output isn't deterministic, so this is the only way back to a specific past agent take), `modified` after every Update round or saved comment, `finalized` once per Finalize (`project_config.yaml` only ever holds the *current* checkpoint — this is the full history). Browsable via a "Load a saved snapshot" section (three dropdowns), which warns before discarding an unsaved in-progress draft.
- Comments accumulate instead of overwriting: `NumericFeatureConfig`/`CategoricalFeatureConfig` gained `comment_history` (`core/schemas.py::CommentEntry`), shown newest-first above each card's comment box, labeled "👤 Actuary" / "Claude" (with the icon at `icons/claude-ai.svg`, see `icons/README.md` for provenance). Legacy checkpoints/snapshots with only a bare `actuary_note` migrate automatically on load (`_migrate_legacy_note`) rather than losing that content.
- Defense-in-depth lesson from this pass: an early version of the refine prompt sent every variable's `comment_history` as an empty `[]`, which was enough for the model to try "helpfully" filling it with a hallucinated flat string, failing validation. - The GLM Fitting step (`glm_coef_workbench.py`) gained a "GLM Distillation version to fit" picker, same current-vs-finalized-snapshot pattern.
- Each stage logs which upstream version it actually used — `feature_source`/`gbm_source`/`distillation_source`, each a `{"kind", "ts"[, "label", "path"]}` dict; `core/snapshot_utils.py` (`snapshot_ts`, `format_ts`) is the one shared place that parses a snapshot filename's or session-log event's timestamp into the plain, comparable form used for this.
- The Audit Trail's "Model Lineage" section (`dashboard/streamlit_app.py`) shows one row per completed stage (GBM Training, GLM Distillation (finalized), GLM Fit) with a "Built from" column in the consistent format `"<Upstream Stage>: <timestamp> (<position>)"`. **The position, not `"(current)"`, is the actual information:** `"current"` always coincides with `"latest"` by construction (Finalize and every picker's own restore branch are the only writers, and both always make the picked version the new current one) — so it told the actuary nothing they couldn't already infer. `"latest"` / `"2nd latest"` / `"3rd latest"` (looked up by position against that stage's own newest-first history) answers the question that matters: was this deliberately built from an older version, and how far back. The "Relativity Chart" sub-tab was removed — it plotted exactly the `exp(coef)` values already in the Rating Factors table, just as a scatter plot.

**Cross-stage staleness detection — 2026-09-06, branch `staleness-detection`:** the sidebar pipeline graph's node/connector distinguishes "not yet run" from "stale" (has run, but an upstream stage has since moved on) — both render dashed, one visual "not solid" state rather than two, since both mean the same thing to the actuary: don't trust this stage's output as current.
- `_source_stale()` (`dashboard/streamlit_app.py`) reuses the cross-stage lineage data that already existed for the "Model Lineage" table: a stage is stale if the upstream source it was actually built from (`feature_source`/`gbm_source`/`distillation_source`) is no longer the newest entry in that upstream's own history — i.e. `_position_label` would no longer call it "latest". No new tracking was needed, only a new consumer of data the lineage work already logs.
- Staleness cascades downstream: GLM Fitting is stale if its own Distillation source is outdated, *or* if GLM Distillation is itself stale (built from an outdated GBM run), *or* transitively if that GBM run was itself built from an outdated feature set — one hop of drift anywhere in the ancestry marks everything below it, not just the stage that directly changed. A hover tooltip on each node names which case applies ("Not yet run" vs. two distinct stale-reason strings — this stage's own source is outdated, vs. its upstream is itself stale) so the actuary isn't left guessing why a completed-looking stage is dashed.
- Feature Selection has no upstream, so it can only be pending/done, never stale.
- **Bug caught immediately by the actuary retraining GBM and seeing no effect:** `_source_stale` originally bailed out (returned "not stale") the instant `source.get("ts")` was missing, so any `feature_source`/`gbm_source`/`distillation_source` logged before `ts` was split out of the picker label (2026-08-30 and earlier — see the finalized-snapshots section above) could never be flagged stale no matter how many newer upstream runs happened. `_fmt_built_from`'s display code already had a fallback for this (parse the timestamp off the label's leading text); `_source_stale` just hadn't reused it. Fixed by extracting `_source_ts()` as the one shared resolver both functions now call, so the two can't disagree about a source's timestamp again.

**GLM Distillation orphaned-term guarantee — same date, same branch:** the staleness warning above is passive (it tells you GLM Distillation is stale after a GBM retrain, but not *what specifically* broke). Retraining GBM after a feature was de-approved surfaced the concrete problem: the existing Distillation draft/checkpoint can still carry a main-effect or interaction term for that now-unapproved feature, and neither Re-open nor Update previously checked for this — an orphaned term could ride along into a Finalize and a fit formula referencing a feature `project_config.yaml` no longer approves. `core/distillation_pipeline.py::reconcile_feature_membership()` closes this, structurally rather than by asking the actuary to remember to check:
- Forces `approved=False` for any term whose constituent feature(s) (split on `":"`, so an interaction is caught if *either* side is orphaned) aren't in the currently approved feature list — reusing `_approved_feature_names(cfg)`, the same helper the workbench already used elsewhere. Stamps a `comment_history` note explaining why (visible via the existing comment-history UI, no new rendering needed) — but only on the actual transition to excluded, and never repeats an identical note, so repeated reconcile passes (Re-open, then Update, then Update again) don't spam the term's history.
- Only ever forces a term *off*, never back on — so a feature that's removed and later re-approved needs no special handling: its old term simply stops being "missing" on the next reconcile and can be re-checked normally in the Not Proposed tab, same as any other actuary-excluded term.
- Called everywhere a draft becomes "the current draft": Re-open, Regenerate from scratch (defense-in-depth — the agent is only ever offered approved features, so a non-empty result here would itself be an anomaly worth surfacing), loading any snapshot (an old snapshot can predate a feature removal too), and both before *and* after every agent refine call in Update/Finalize — the same "before and after any agent call" cadence `reconcile_terms` already uses, so a re-checked box or an agent's refine response can't reintroduce an orphaned term while its feature stays unapproved. `st.warning()` names exactly which terms got auto-excluded, once, right where it happens.
- **Deliberately not built:** a hard block on Re-open when the GBM run has changed (floated, then set aside). The real invariant that has to hold is feature-membership, not GBM-run identity — a retrain that only changes H-statistics without touching the approved feature set invalidates nothing, and the existing "GBM run to distill from" picker already lets the actuary deliberately regenerate against an older run, which a hard identity gate would contradict. The narrower, correctness-driven fix above covers the actual failure mode without blocking a legitimate workflow.
- **Two real bugs found by actually driving the dashboard (Playwright, headless Chromium) against a live scenario, not just unit tests:**
  1. `st.warning()` called immediately before `st.rerun()` (the pattern used at every call site above) never reaches the browser — `st.rerun()` raises an exception that aborts the script run before that message is ever seen, and the fresh run Streamlit starts next doesn't re-emit it. Confirmed empirically (screenshot showed no banner). Fixed by stashing the message in `st.session_state.glm_feature_membership_notice` and popping/rendering it once at the top of `render_glm_workbench` — the one entry point every subsequent render passes through regardless of which view ends up showing. This is a general Streamlit gotcha, not specific to this feature; other `st.success(...)`/`st.info(...)` calls elsewhere in this file that immediately precede `st.rerun()` likely have the same defect, not yet audited.
  2. `dashboard/glm_workbench.py::_approved_feature_names()` never actually filtered by `approved` — it returned every name in `features.numeric`/`features.categorical` regardless of rejection, which is what made `reconcile_feature_membership` a no-op in the first empirical test (a rejected feature was still "in the approved list" as far as this helper was concerned). Pre-existing, unrelated to this branch's own work, but it also means "Regenerate from scratch" had been feeding rejected features to the LLM as candidates, and the "Not Proposed" tab could offer to promote a main effect for one. Fixed to filter on `approved is not False`, matching the convention used everywhere else (`feature_workbench.py`'s checkbox default, `streamlit_app.py`'s own `approved_numeric`/`approved_cat`).
  3. Both re-verified live end-to-end after the fixes: de-approved a real feature (`vehicle_age`) in `project_config.yaml`, clicked Re-open, and confirmed via screenshot that the warning banner renders, the term counts move (Main Effects 15→14, Interactions 32→30, Not Proposed 73→76), and the excluded card in "Not Proposed" carries the auto-added Claude note explaining why.

**"Minimal-diff refinement" generalized and named — same date, same branch, prompted by the actuary thinking through the orphaned-term work above more deeply:** the actuary's own framing — an Update round built from an existing snapshot should change as little as possible; add a newly-approved variable without touching anything else, drop a removed one without touching anything else — is the same principle `reconcile_feature_membership` above already embodies for feature-membership, generalized to *content*. Investigating turned up that the codebase already had two narrow, inconsistent instances of it (`refine_draft`'s categorical `grouping` carry-forward; a weaker version for excluded-column `exclusion_rationale`/`excluded_description` that only triggered when the LLM omitted the field entirely, not when it reworded one unprompted) but nothing at all protecting the actual descriptive content — a `GLMTerm`'s `rationale`/`h_statistic`, a feature's `description`/`data_quality_note`/`ordinal`/`order`/`n_clusters` — despite both refine prompts already telling the model to leave untouched items alone (prompt-level only, the same gap this document's other structural-guarantee decisions all warn against trusting). See the "Key design decisions" entry above for the principle itself. **Run-scoped config/reports layout — 2026-09-08, branch `run-scoping`:** the actuary's stated goal for this pass was making the dashboard usable by someone bringing their *own* dataset — but a different dataset means different target/exposure column names and invalidates the seed files (which name specific columns), and everything downstream (feature checkpoint, GBM, GLM) is meaningless once the target changes underneath it. A single mutable `config/`+`reports/` pair had nowhere consistent for a second dataset's state to live without silently mixing with the first.
- **Design, converged over several rounds of discussion:** a sidebar-editable Setup UI (the initial idea) was explicitly abandoned in favor of the simpler, established convention this codebase already uses for `feature_seed.yaml`/`distillation_seed.yaml` — hand-edited YAML, no UI, no auto-anything. `<name>/` is a top-level folder, a peer of `agents/`/`core/`/`dashboard/` (not nested under an intermediate wrapper), bundling `config/` and `reports/` together for one dataset + target configuration — confirmed explicitly as its own requirement ("`<name>` must be on top of everything we have implemented so far"), since config and reports must invalidate as one unit or a "reset" session log could sit next to stale checkpoints from the old target.
- **`active_run.yaml`** at the repo root (outside every `<name>/`, since it has to be findable before any name is known) holds the one field naming the active run. **`core/run_scope.py`** is the single place all path derivation lives: `default_config_path()` is the *only* function that reads the pointer; every other helper (`reports_dir`, `sessions_dir`, `drafts_dir`, `decisions_log_path`, `gbm_model_path`) takes an explicit `config_path` and derives siblings from it, so the same code resolves correctly for the active run, a deliberately reopened old one, or a test's `tmp_path` config — no global state outside the one pointer read.
- **`create_run(label)` / `open_run(name)`**, not one combined function: `create_run` always appends a timestamp (`<label>_<timestamp>/`), so a collision with an existing folder is structurally near-impossible rather than merely checked-for (an `assert`-style guard still refuses outright, belt-and-suspenders); `open_run` takes the *exact* existing folder name and just switches the pointer, no fuzzy matching, no auto-resume-by-matching-config-values — the actuary types the name they want, same discipline as everywhere else in this design. Both are also reachable as a tiny CLI (`python -m core.run_scope create|open|validate`) so a terminal-only workflow needs no Python REPL.
- **`validate_config()`** is a consolidated startup check (called once by `Orchestrator.__init__` and once by the dashboard) rather than three separate scattered checks: raises for anything that makes a run unusable (missing run folder, missing/unparseable `project_config.yaml`, a required `data.*` key absent, the dataset file itself missing) and returns non-fatal warnings for a `feature_seed.yaml`/`distillation_seed.yaml` entry naming a column that isn't actually in the dataset (reads only the CSV header, not the full file). This was deliberately chosen over a passive dashboard note alone — the concrete, checkable failure (a seed's `name` field vs. the dataset's real columns) is what actually breaks, so it's checked, not just hinted at.
- **What's deliberately not built:** no dataset upload/path picker in the dashboard — `data.path` stays hand-edited in `project_config.yaml`, same as before this branch; the actuary's motivating goal (support a bring-your-own-dataset workflow) is served by making the run-folder mechanics correct, not by adding a file-upload widget, which was explicitly scoped out as a separate, bigger feature. **Target-leakage warning + missing-value visibility — 2026-09-08, branch `target-leakage-and-missing-value-warnings`, picking up `target_leakage_validation_deferred`:** both ideas that memory note raised, built and code-computed rather than LLM-guessed, same doctrine as every other "structural guarantee, not just prompt-level" decision in this document.

**GBM H-statistic crash on categorical features fixed — 2026-09-09, branch `fix-gbm-categorical-h-stat-crash` (merged to main):** training the GBM on a real run hit `TypeError: Invalid value '6.736842105263122' for dtype 'int8'` inside H-statistic computation. Root cause: `tools/shap_tools.py`'s partial-dependence grid builder (`_feature_grid`) built every feature's grid via quantile interpolation, including label-encoded categoricals — `GBMAgent._prepare_data` converts each approved categorical to integer codes via `.cat.codes`, whose pandas dtype is the smallest int type that fits the cardinality (`int8` under 128 categories). Interpolating between category codes synthesizes a fractional "category" that doesn't exist (e.g. `6.7368...`) — meaningless for a partial dependence on its own, and it crashes when written back into the codes' integer-dtype column: pandas 2.x/3.x raises rather than silently upcasting on a dtype-incompatible `.loc` assignment. The bug was latent from the start (any grouped categorical whose cardinality sat near the `h_stat_grid_size` default of 20 was at risk) and only surfaced once a feature's category-frequency distribution happened to make a quantile position land off an integer.
- `compute_h_statistics` now takes `cat_cols` (threaded from `GBMAgent._cat_cols`) and, for a categorical feature, builds its grid from the actual unique codes present — evenly subsampled down to `grid_size` if there are more codes than that — instead of quantile-interpolating between them.
- `_pd_1d`/`_pd_2d` also widen a target column to float before writing a grid value into it, as a general safety net for any genuinely numeric feature that happens to be integer-dtype in the source data — LightGBM predicts on the values, not the pandas dtype, so this is safe regardless of the column's original dtype.
- Verified two ways: a standalone reproduction against the actual `motor_portfolio_20260908_190139` run's approved feature set (crashed on the pre-fix code, trained cleanly — 105 pairwise interactions, 0 errors — after the fix), and the actuary's own live retrain in the dashboard on the same run (see the run-scoping section's target-leakage entry above, whose feature-selection fix this retrain also carried out).

This was the exact asymmetry the GLM Distillation Workbench's "Not Proposed" tab note above used to call out as a known Feature Workbench limitation, not a fresh regression.
- **Root cause:** `core/feature_pipeline.py::reconcile_membership()` demoted an unchecked numeric/categorical feature from its full `NumericFeatureConfig`/`CategoricalFeatureConfig` object down to a bare column name plus a single `exclusion_rationale` string the instant it was unchecked — discarding `comment_history` (and any earlier Claude reply) entirely, before Update/Finalize's own comment-saving logic ever got a chance to matter.
- **Fix, structural rather than a rendering patch:** an unchecked feature now just gets `approved=False` in place — it stays the same object, in the same `numeric`/`categorical` list, so its `comment_history` survives untouched. `dashboard/feature_workbench.py::_render_cards` partitions numeric/categorical into shown (`approved is not False`) vs. hidden (`approved is False`) and renders a hidden one in the Not Proposed tab via the same full-card path (comment history, Claude icon) as any other card — the true bare-name fallback is now reserved only for columns the agent never proposed a card for at all.
- **The one subtlety this touched:** the refinement prompt's `previous_proposal_json` shape was never designed to see an `approved: false` entry sitting inside "numeric"/"categorical" — it only ever expected that to mean "still included." Rather than trust the prompt's "shape must match" instruction to route a demoted feature through the round-trip unmolested (the exact kind of prompt-only enforcement this document's other structural-guarantee decisions all warn against), `agents/feature_selection_agent.py::refine()` temporarily represents a demoted feature as a bare `excluded` name for the LLM call only (`_flatten_demoted`), then restores the real object (comment_history intact) once the response comes back (`_restore_demoted`) — mirroring the existing `_strip_locked`/`_merge_locked_entries` pattern already used for seed-locked columns in the same file. A reply the LLM writes for a feature actually remarked on this round is folded into `actuary_note` (so it reaches comment_history through the same path as any other feature's reply); an unremarked feature's carried-forward rationale is never folded in, or the actuary's own prior comment would get re-appended to their own history mislabeled as a Claude reply.
- Covered by new tests in `tests/test_feature_pipeline.py` (reconcile_membership keeps the object in place, comment_history survives) and `tests/test_feature_selection_agent.py` (the flatten/restore round-trip, remarked vs. unremarked). Verified live end-to-end by both the actuary and Claude independently in the running dashboard — unchecked a real feature with a comment, clicked Update, confirmed the comment and a live Claude reply both render on the Not Proposed card.
- **Not touched, same limitation as before this fix:** after Finalize, the locked view still reconstructs excluded columns generically from `project_config.yaml` (which never persisted excluded content, by design) rather than from the richer in-session draft — the full comment history for a *finalized* exclusion lives in the `finalized` draft snapshot instead, browsable via "Load a saved snapshot," same as it always has for the agent's own original exclusions.

**Run folders grouped under `runs/` — 2026-09-10, branch `runs-folder`:** every `<name>/` run folder (config + reports for one dataset + target configuration, see "Run-scoped config" above) previously sat directly at the repo root, alongside `agents/`, `core/`, `dashboard/`, etc. — fine for one or two runs, but each new run added another top-level entry with no grouping, cluttering the root listing. Purely a path change, no data-model or checkpoint-shape change.
- **`core/run_scope.py::runs_dir()`** (new) returns the single `repo_root() / "runs"` folder every run now lives under. `default_config_path()`, `create_run()`, and `open_run()` were the only three functions that ever built a run's path directly off `repo_root()` — each now goes through `runs_dir()` instead. Every other helper in the module (`run_root`, `reports_dir`, `sessions_dir`, `drafts_dir`, `decisions_log_path`, `gbm_model_path`) already took an explicit `config_path` and derived siblings from it, so none of them needed to change at all — the same "one function reads the pointer, everything else takes an explicit path" design the original run-scoping work put in place is exactly what made this a small, contained move rather than a scattered one.

## Run-scoped config

Config and `reports/` live under a top-level `runs/<name>/` folder — one per dataset +
target configuration, e.g. `runs/motor_portfolio_20260620_103855/` — not at fixed
repo-root paths, and grouped under the single `runs/` folder rather than each `<name>/`
sitting directly at repo root (added 2026-09-10, see "Runs folder" below — the earlier
run-scoping work below still put `<name>/` straight at repo root). `active_run.yaml` at
the repo root names which `runs/<name>/` is active; every path below is relative to it.
See `core/run_scope.py` (`create_run`, `open_run`, `runs_dir`, `validate_config`, also
usable as `python -m core.run_scope {create,open,validate}`).
Switching runs is entirely hand-driven — no dashboard UI, no auto-naming, no
auto-detection — deliberately, to keep target/exposure/dataset changes rare and explicit
rather than another actuary-facing workflow to build and maintain.

afterward; anything not passed keeps the template's placeholder, still needing that
hand-edit. `validate_config` also checks `target_col`/`exposure_col` actually name

placeholder or typo would otherwise pass validation silently.

## Key design decisions

- **Agent-output overrides (`core/overrides.py`) — three named, reusable mechanisms for making sure a field the LLM regenerates every round can never be that field's real source of truth:** every refine call (`FeatureSelectionAgent.refine`, `DistillationAgent.refine`, `GroupingAgent.refine`) sends back a complete, freshly-generated proposal — main effects, interactions, descriptions, groupings, all of it — regardless of how narrow the actuary's remark was, and at a non-zero temperature (0.2) nothing guarantees that regeneration reproduces an untouched item's content, or an actuary-controlled flag, the way it was left. Originally three independent, ad hoc pieces of code scattered across `feature_pipeline.py`/`distillation_pipeline.py` (raised for consolidation 2026-09-07, see the memory note `guardrails_consolidation_deferred`, deliberately deferred at the time); consolidated 2026-09-10, branch `consolidate-overrides`, into one module once it became clear all three shared the same underlying purpose. Deliberately a different species from the more common "guardrail" meaning (Guardrails AI, NeMo Guardrails, moderation/schema validation) — those check one output against a fixed rule, stateless with respect to prior rounds; everything here is stateful across rounds, comparing this round's output against what came before or against a live external source.
  **`pin_unchanged_fields`** — *minimal-diff refinement*: an actuary's Update round changes only what was remarked on, never anything else. Every item that both existed before and wasn't named in this round's `changed` set gets each of a caller-supplied `fields` tuple forced back to its exact prior-round value, discarding whatever the LLM returned for it. `core/feature_pipeline.py::refine_draft` calls it with `("description", "data_quality_note", "ordinal", "order", "n_clusters")` for every numeric/categorical feature; `core/distillation_pipeline.py::refine_glm_draft` with `("rationale", "h_statistic")` for every `GLMTerm`. An excluded column's `exclusion_rationale`/`excluded_description` is dict-shaped rather than object-attribute-shaped, so that one stays a small inline block in `refine_draft` rather than being forced through this helper. Two things are exempt: an item the actuary *did* remark on this round, and a brand-new item with nothing to pin from.
  **`force_field_from_authority`** — a field the agent never owned to begin with, re-set from a human-owned source on *every* call, not just an unremarked one: `core/feature_pipeline.py::reconcile_membership` uses it to force every numeric/categorical feature's `approved` flag from the actuary's checkbox state (default `False` for anything the checkboxes don't cover); `core/distillation_pipeline.py::reconcile_terms` uses it the same way for a GLM term's `approved` flag, but with `only_if_present=True` so a term the agent proposed this round that the actuary hasn't seen yet is left as returned rather than forced to a default.
  **`ratchet_exclude`** — a one-way lock: an item is forced out the moment a caller-supplied validity check says it's no longer valid, with a note explaining why, and never silently re-included later even once it becomes valid again — restoring it is always a separate, deliberate action. `core/distillation_pipeline.py::reconcile_feature_membership` uses it to exclude a GLM term whose constituent feature(s) are no longer in the approved feature set (an orphaned term from a de-approved Feature Selection column), supplying the `":"`-split validity check and the comment-history note (deduped so repeated calls don't spam identical notes).
  All three share one doctrine with every other "structural guarantee, not just a prompt instruction" decision in this document (the seed-config `temperature==0.0` lock, comment-history's prompt-omission-plus-validator): never trust a non-deterministic model to leave something alone or respect a human's decision just because the prompt asked it to — several of these prompts (`prompts/distillation.yaml`'s `refinement` section, `prompts/feature_selection.yaml`'s) *already* say some version of the right thing, which is necessary context for the model but was never sufficient enforcement on its own. `tests/test_overrides.py` covers all three functions directly; `tests/test_feature_pipeline.py`/`tests/test_distillation_pipeline.py` cover them through each pipeline's own reconcile/refine calls.
- **GBM-first, not hypothesis-first:** the GBM reveals what the data says; the LLM and actuary then decide what goes into the GLM. More grounded than speculative hypothesis generation.
- **H-statistics only (not SHAP interaction values):** Friedman H-statistics are fast to compute on large datasets. Full SHAP interaction values on 354k rows are prohibitively expensive. H-stats are sufficient for ranking interactions for the distillation agent.
- **Top-N feature cutoff for H-statistics:** only pairs among the top-N features (by LightGBM gain importance) are evaluated. Configurable via `gbm.top_n_features` in project_config.yaml.
- **No hyperparameter tuning (Optuna):** the GBM is an instrument for finding interactions, not the deliverable. Reasonable defaults + early stopping produce correct interaction rankings without the 30+ min tuning overhead.
- **Log-rate target for GBM:** MSE on `log(total_premium / total_exposure)` — the annualised pure premium rate. This dataset stores the **earned (pro-rata) premium**, confirmed empirically: `corr(total_premium, total_exposure) ≈ 0.60` and dividing by exposure reduces the CV (0.77 → 0.57). If a dataset stores the annual tariff premium instead, exposure and premium would be uncorrelated and no division would be needed.
- **Prompts in `prompts/` YAML files:** separated from code, easy to iterate without touching Python. Each file has named sections (`proposal`, `refinement`) used by the corresponding agent. `feature_selection.yaml` and `distillation.yaml` are actively used; `grouping.yaml` exists but the grouping agent uses inline prompts (`GROUPING_PROMPT` / `GROUPING_REFINE_PROMPT` in `agents/grouping_agent.py`).
- **Pairwise interactions only in the GLM:** H-statistics are inherently pairwise, so the distillation agent is restricted to proposing main effects and two-feature interactions. Three-way interactions are not proposed automatically — the actuary can add them via the remark loop if needed.
- **Actuary-in-the-loop at every stage:** feature selection, grouping, and GLM term selection all have an approve/reject/remark gate. Remarks loop back to the LLM for refinement.
- **Checkpoint pattern:** approved decisions are written back to YAML. Re-running skips already-approved stages.
- **Pydantic for all LLM outputs:** malformed JSON surfaces as a clear `ValidationError` immediately.
- **Prompt caching:** system prompt cached in `LLMClient` — reduces cost on repeated calls.
- **Temperature 0.2:** stable enough for actuarial reasoning, slight variation improves proposal diversity.
- **LangGraph-compatible:** all agents are stateless classes with typed inputs/outputs.
- **Post-fit coefficient review gate (GLM):** after the initial fit, the actuary reviews every term's coefficient sign, p-value, and CI. A rejected term is dropped and the model is immediately refit — the loop repeats until a clean pass. This catches suppressor variables and levels with sparse data that the distillation gate (which reviews LLM proposals, not fitted parameters) cannot detect.
- **Rating factors as relativities, not log-coefficients:** `exp(coef)` per parameter is shown as a multiplicative relativity (base = 1.0 for the reference level). This is the direct pricing output actuaries use.
- **No explainerdashboard:** explainerdashboard runs a separate Dash server and doesn't natively support statsmodels GLMs. Diagnostics for the GLM (deviance residuals, Q-Q) and GBM (SHAP summary) will be rendered natively in the Streamlit dashboard using matplotlib/shap, keeping it as a single-pane-of-glass UI.
- **max_tokens=8192:** the distillation agent's JSON response (main effects + interaction terms for all approved features) can exceed 4,000 tokens. The client is set to the model maximum of 8,192.
- **Session logging (JSONL):** every pipeline run writes a JSONL file to `<run>/reports/sessions/`. Each event (proposal, decision, remark, GBM metrics, GLM fit) is flushed immediately so partial runs are preserved. This is the data source for the dashboard's Layer 1 read-only views (Audit Trail, and — for now — GLM Results; see "Known issues" above).
- **Run-scoped config/reports, hand-managed rather than dashboard-driven:** `<name>/` bundles one dataset + target's config and reports together (see "Run-scoped config/reports layout" above) — a structural guarantee that a target/dataset switch can't leave a stale checkpoint next to a reset session log, deliberately kept to plain YAML + a CLI (`core/run_scope.py`) rather than another actuary-facing Streamlit workflow, matching this project's existing seed-config convention (hand-edit, no UI) rather than inventing a new one.
- **Dashboard layered build:** Layer 1 is a read-only Streamlit viewer of session logs. Layer 2 (complete, 2026-08-08) replaces terminal gates with Streamlit interactive forms, one workbench per gate, all writing the same checkpoints the CLI reads.
- **Checkpoints over session-log events for anything the dashboard can retrain:** the GBM checkpoint (`gbm_output` in `project_config.yaml`) stores `feature_importances` alongside `interactions` specifically so the dashboard never has to fall back to a possibly-stale session-log event to render current results. Applied to GBM; not yet applied to the GLM's fitted results (see "Known issues").
- **Checkpoint invalidation on feature-set change:** finalizing the Feature Workbench with a different approved feature set (names or categorical groupings, compared via `_feature_signature`) clears any existing `gbm_output`/`glm_config.yaml` terms, since both downstream stages otherwise skip re-running whenever *any* checkpoint exists — a stale feature set could silently survive into training without this.
- **Shared `core/*_pipeline.py` modules:** checkpoint read/write and training/fitting logic for features, GBM, and GLM each live in one module (`core/feature_pipeline.py`, `core/gbm_pipeline.py`, `core/glm_pipeline.py`, `core/distillation_pipeline.py`), used identically by `agents/orchestrator.py` and the dashboard workbenches. `dashboard/_session.py` similarly shares the LLM client, cached dataframe, and session logger across every Layer 2 tab in one browser session, so one dashboard visit produces one coherent session log regardless of which workbenches get used.
- **Seed configs (`core/seed_config.py`):** optional, hand-edited YAML priors (`feature_seed.yaml`, `distillation_seed.yaml`) distinct from the checkpoint configs above — a seed is a stable, rarely-changing input, not an accumulated/invalidated result. Per-entry `temperature` (0.0–1.0) governs how much license the *agent* has to deviate, never the actuary's own override power: `temperature == 0.0` is enforced in `FeatureSelectionAgent`/`DistillationAgent` at the code level — the column/feature is stripped from what's profiled and sent to the LLM before the call, so it structurally cannot be reconsidered, not just prompt-instructed not to be. `temperature > 0.0` stays visible to the LLM with a prompt note on how much license it has to suggest an alternative. An actuary remark on a locked entry during a refine round lets it through for that round only — the lock restrains the agent's *unprompted* behavior, never an explicit actuary instruction. No seed-authoring UI yet (hand-edit the YAML, same as pre-populating `project_config.yaml`) and no `updated_at` staleness badge in the dashboard yet (see "Next planned work").
- **Comment history is code-owned, never the LLM's to populate:** `NumericFeatureConfig`/`CategoricalFeatureConfig.comment_history` accumulates across rounds; `actuary_note` is a transient single field the LLM writes its reply into for the current round only, immediately folded into history and cleared by `core/feature_pipeline.py::refine_draft`. The refine prompt never shows the model `comment_history` at all — same rationale as the seed-config locks, applied to a new surface: don't just ask the model not to touch something, structurally keep it from seeing the field in the first place, and defend with a schema-level validator in case a future prompt change reintroduces it.
- **Snapshot kinds are declared, never inferred:** `initial`/`modified`/`finalized` under `<run>/reports/drafts/` are written by exactly the action that produces that kind of draft (a fresh LLM call, an Update round, a Finalize) — there's no logic anywhere that guesses a snapshot's kind after the fact from its content.
